<Layer kind="concept">

The second family keeps the GPU's memory system (weights in HBM) but builds its matrix engine differently: a few large **systolic arrays** in which each weight sits in one processing element while activations flow past it, so a weight read once from memory is used by every row that streams through. Two shipping lines say so in their own documentation. Google's TPUs: "an MXU is composed of either 256 x 256 (TPU v6e and TPU7x) or 128 x 128 (TPU versions prior to v6e) multiply-accumulators in a systolic array". AWS Trainium: the NeuronCore's "Tensor engines are based on a power-optimized systolic array", organised "as a grid of 128x128 processing elements". How such an array works cycle by cycle is the whole of [Systolic Arrays Explained](https://systolic-arrays-explained.vercel.app/learn/02-weight-stationary); this chapter is about what the design means for the running workload.

The array is a fixed pipeline, so the compiler, not the hardware, plans every transfer: Google's TPUs take their programs through XLA, and VMEM, the on-chip scratchpad in front of the MXUs, is sized and filled by the compiler and by custom kernels rather than by a cache.

<span id="a-array" />

The animation runs one 1,024 × 1,024 matmul. Each tile of weights holds the array for $\max(m, R)$ cycles: the $m$ input rows of the batch take $m$ cycles to stream through, and the next tile's $R$ rows of weights take $R$ cycles to shift in behind it. With a batch of 1 the array spends 1 cycle in <V of="mxu(256,256,1,1024,1024).per_tile" fmt="int" /> multiplying, so one decoder layer of the 70B model uses <V of="layerMxu(256,256,llama3-70b,1).util" fmt="pct" /> of a 256 × 256 array. At a batch of 16 it uses <V of="layerMxu(256,256,llama3-70b,16).util" fmt="pct" />; at a batch of 256, <V of="layerMxu(256,256,llama3-70b,256).util" fmt="pct" />. A 128 × 128 array fills at half the batch: <V of="layerMxu(128,128,llama3-70b,128).util" fmt="pct" /> at 128. The big array's lesson for decode is the GPU's, sharpened: it wants a batch at least as tall as itself.

## The running workload on systolic chips

<span id="a-decode-sys" />

Because the weights live in HBM, decode on these chips is bounded the way it is on a GPU: by bytes over bandwidth. TPU7x reads its <V of="part.tpu-7x.off_bytes" fmt="bytes" /> of HBM at <V of="part.tpu-7x.off_bw" fmt="rate" />, so Llama 3.1 70B in FP8 fits on one chip and a batch-1 step is bounded at <V of="decode(tpu-7x,llama3-70b,fp8,1,1024).t_step" fmt="time" />. Trainium2 holds it in <V of="part.trn2.off_bytes" fmt="bytes" /> and reads at <V of="part.trn2.off_bw" fmt="rate" />: <V of="decode(trn2,llama3-70b,fp8,1,1024).t_step" fmt="time" />. TPU v6e has <V of="part.tpu-v6e.off_bytes" fmt="bytes" /> per chip, so the 16-bit model needs <V of="decode(tpu-v6e,llama3-70b,bf16,1,1024).chips" fmt="int" /> chips. The ridge points are GPU-like too: <V of="ridge(tpu-7x,fp8)" fmt="num" /> flops per byte for TPU7x in FP8, <V of="ridge(trn2,fp8)" fmt="num" /> for Trainium2. Its successor, Trainium3, is not in this site's model: AWS gives it "144 GB HBM3e per chip, 4.9 TB/s bandwidth - 1.7x higher than Trainium2" and "up to 2x MXFP8 compute throughput compared to Trainium2", in UltraServers of up to 144 chips ([AWS Trainium](https://aws.amazon.com/ai/machine-learning/trainium/), read 2026-10-16; [Racks, chapter 10](https://ai-racks-explained.vercel.app/learn/10-other-designs) uses those figures).

What differs from a GPU is the machine around the array: one large compiled program instead of many kernels, a scratchpad instead of a cache, and, at scale, the TPU pods' torus of chip-to-chip links ([AI Racks Explained, chapter 10](https://ai-racks-explained.vercel.app/learn/10-other-designs)). Google and AWS do not state their chips' power in the sources used, so this chapter gives no energy per token for them.

<Callout kind="illustrative">

The tile model assumes the next tile's weights load behind the current one at one row per cycle, and charges one fill and drain per matmul; it leaves out the vector unit's work (softmax, normalisation) and the HBM traffic that feeds the tiles. The 1,024 × 1,024 matmul is sized to fit the picture; the per-layer utilisation uses the 70B model's real matrix shapes. Trainium2's interconnect figure is stated without a direction and is shown as given.

</Callout>

<Layer kind="maths">

A weight-stationary array of $R \times R$ processing elements running an $m \times k$ by $k \times n$ matmul works through $\lceil k/R \rceil \lceil n/R \rceil$ tiles. With the next tile's weights shifted in behind the current one, a tile holds the array for $\max(m, R)$ cycles, and the first fill and last drain add $2R - 2$:

$$
C = \left\lceil \frac{k}{R} \right\rceil \left\lceil \frac{n}{R} \right\rceil \max(m, R) + 2R - 2,
\qquad
U = \frac{m k n}{R^2 C} \;\approx\; \frac{\min(m, R)}{R} \text{ for large } k, n.
$$

So a batch below $R$ uses about $m/R$ of the array, whatever the matrix.

</Layer>

One matmul on the array, cut from [`src/lib/accel/model.ts`](https://github.com/BrendanJamesLynskey/ai-accelerators-explained/blob/main/src/lib/accel/model.ts):

```ts
const tiles = Math.ceil(k / rows) * Math.ceil(n / cols);
const perTile = Math.max(m, rows);
const cycles = tiles * perTile + rows + cols - 2;
const macs = m * k * n;
```

<Remember>

- Systolic chips keep the GPU's memory system and build the matrix engine as a few large arrays.
- A weight tile holds the array for $\max(m, R)$ cycles, so a batch below $R$ uses about $m/R$ of it.
- The compiler (XLA on TPUs) plans every transfer; a scratchpad replaces the cache.
- With weights in HBM, decode is bounded by bytes over bandwidth, as on a GPU.
